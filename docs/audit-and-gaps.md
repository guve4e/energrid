# Documentation audit and remaining gaps

### M1.4e — scoped commissioning-event persistence (locally validated, not deployed)

New commissioning events use `event-v2:<encoded tenant>:<encoded site>:<encoded device>:<encoded event id>` and require explicit ownership. Scoped readers return only exact tenant/site/device matches. The Portal commissioning-event endpoint resolves its authorized site from the authenticated principal and checks the device in that scope before reading history. The registry rejects ambiguous device-ID-only event writes; callers with trusted ownership can supply it explicitly. Legacy `event:<device id>:<event id>` records are preserved but **not** exposed through scoped reads or automatically assigned to any site; offline inventory and a reviewed migration are still required. This is not a durable, tamper-evident audit ledger.

**Scope limitation:** other legacy Portal commissioning mutation routes still resolve devices by ID alone; this change does not make them tenant-isolated. Run the focused storage, Portal, and registry tests, API typecheck, and broad regression suite before acceptance. No live LevelDB migration or deployment is included.

### M1.4d candidate — scoped installation/proposal persistence (test verification pending)

`DeviceInstallationStore` writes new installations under `installation-v2:<encoded tenant>:<encoded site>:<encoded device>` and new proposals under `installation-proposal-v2:<encoded tenant>:<encoded site>:<encoded proposal id>`. All installation/proposal reads require explicit tenant/site scope; the store does not accept site-only lookup. Legacy reads use their embedded tenant/site ownership and never infer missing ownership. All-site bootstrap retains a versioned record in preference to its legacy copy. New proposal decisions must hide older pending legacy copies.

This candidate **does not migrate, rewrite or delete legacy keys**, and does not address unscoped commissioning event keys or the Portal's event endpoint. Before rollout: inspect an offline LevelDB copy for missing ownership and duplicate/conflicting legacy records, back up the live store, validate restart and older-version rollback constraints, then run the full tests. Reverting application code after v2 writes would not expose those writes to an older binary; a backup alone is not a lossless rollback after subsequent writes. No live DB, deployment, or hardware validation has occurred.

M1.4a does **not** establish complete cross-tenant isolation or authorize new device control.

### Known unresolved defects / acceptance gaps

- **Bathroom status projection and stale-state isolation remain open:** API logs confirm the `pi-upstream-bathroom` observer passed validated status to the canonical writer, and the Portal timestamp advanced over its connected SSE stream. The Portal status card nevertheless says current connectivity is not confirmed; verify whether the existing projection intentionally reports status-source connectivity separately or is missing the observer-reachability projection. API restart recovery passed: the worker was recreated and accepted a subsequent sample. A controlled pause of only that worker did not make the device stale because an independently configured MQTT source continued updating it. Do not disable other sources merely to manufacture staleness. A valid stale test must establish that every authorized source for this device has stopped, then confirm freshness expires while the last-known relay value is retained.
- **Observer configuration precedence:** API `main.ts` loads ignored `.env.auth.local` with override semantics, so this file—not the WebStorm run-configuration value—is the effective source of `HOME_SITE_LOCAL_OBSERVERS_JSON`. The exact Home/upstream allowlist for Bathroom ID and `switch:0` is present in that local file. It is local-only and must not be committed. Authorization configuration is not itself proof of a running observer; the worker and its accepted observations must be verified separately.
- **Live event synchronization:** SSE code and tests exist, but measured external device change-to-Portal latency and live API restart recovery remain unverified for Home hardware.
- **Physical Bathroom switching acceptance remains blocked:** the execution route is configured and read-only verification succeeds, but the attached load has not been identified as safe. Do not send `Switch.Set` until the operator confirms the connected load is safe and explicitly authorizes a physical test. Virtual Lab command/readback does not establish physical readiness.
- **Collection scale/retry policy:** the HTTP collector still uses unbounded per-cycle `Promise.all` and lacks per-device backoff/jitter; collection coordinator work remains roadmap, not implemented.
- **Background MQTT ownership/history convergence:** normal configured routes and legacy adapter effects do not all traverse the common ingress/history writer. The existing limitation remains documented in [Collection and ingestion](collection-and-ingestion.md) and ADR 0002.
- **Durable user-attributed device command audit:** current registry command/runtime logs are not a durable append-only command ledger; see [Commands and authority](commands-and-authority.md).
- **Generic HTTP reachability semantics:** some generic configured HTTP failures still project `offline` without observer-relative context; see ADR 0004.

## Weather forecast tile renderer V1 status

The renderer and public Core tile route are in the weather release commit, with focused coverage for run-pinned WCS requests, PixelIsArea alignment, transparent zero, missing data, intensity values, adjacent XYZ continuity, exhausted WCS no-data, network failure and recovery. The service validates each requested run and valid hour against DWD capabilities. Per-process upstream work is capped at four active requests and 24 queued; peer queues are round-robin, capped at three active and 16 queued per socket address. Core enables permissive CORS globally, and a reverse proxy collapses caller identity unless it is explicitly and safely propagated. These limits do not replace ingress-level per-client request limits.

**Weather upstream reliability (Patch 04, focused local verification passed; not deployed):** DWD upstream fetches already have a 12-second HTTP deadline, per-process concurrency caps, and no-data retries. Both river HTML sources share a 10-second fetch deadline and 1 MiB response cap; provider failures continue to return unavailable readings rather than invented measurements. Focused transport tests are included. This does **not** implement caller-disconnect cancellation, multi-process admission control, upstream health telemetry, authoritative river timestamps, or public ingress rate limits. Focused tests and build checks passed locally. Production routing, runtime acceptance and deployment remain unverified.

## Rainfall coverage integrity (patch proposal, 4 November 2026)

The Weather Core's `assessRain` now requires 24 consecutive hourly slots with finite, nonnegative precipitation and valid rain probabilities before classifying a 24-hour period as dry or calculating 24-hour totals. A short forecast, a gap, or a missing value produces an **unknown** outlook with null amounts and an explicit count of consecutive valid hours. The 6-hour immediate risk assessment remains independent of this longer rainfall horizon. The Portal renders unavailable amounts as dashes and labels incomplete rain-data coverage. Missing daily precipitation totals remain null.

This patch was prepared against the 4 November review ZIP, not committed, merged, deployed or verified against the live repository or a running environment. Acceptance requires applying it to the current local checkout, running the focused Core/Portal tests and type checks, reviewing the diff, and recording actual results before merging. The broader investigator event-identity, severity validation, retention, provider reliability and notification-delivery issues remain open.
