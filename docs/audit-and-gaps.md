# Documentation audit and remaining gaps

## M0 — Home authority and local Shelly evidence contract (5 November 2026)

**Verified runtime distinction:** the local Mac API and Pi 5 API are separate instances with separate PostgreSQL databases, local observation/discovery stores, broker settings, and configured network scopes. Both can report `tenant-demo/site-home`; that label is not a replication contract. At the read-only comparison for this milestone, Mac had 10 active Home enrollments in its local databases while Pi 5 had 3 active Home enrollments in its production database. Shared protocol identities have different Physical Inventory IDs in those independent stores. No data was copied, and inventory IDs must not be transferred between environments. Pi `.6` is a separate host and is not the API authority. The Pi 5 remains the proposed Home site authority; this change does not migrate or deploy it.

**Source correction (local, not runtime-accepted yet):** selected-device verification previously gathered fresh local Shelly RPC responses but saved only the legacy `http_rpc` claims. The EM1 read-route requires verified `http_identity` identity plus `site_local_http_rpc` observer/interface/component evidence, so it correctly rejected that incomplete record with `saved_identity_or_component_evidence_missing`. For enrolled devices, the Portal also could not offer refresh, and its “verified” projection did not enforce the 15-minute freshness contract. The verifier now requires the configured local observer to match tenant, site, scope, host, interface and directly attached CIDR; resolves the exact enrolled physical/component assignment; persists verified identity and component provenance through existing Discovery Memory and reconciliation writers; and carries a site-observer scan marker and completion time. The Portal exposes a refresh action only for an exact assigned enrolled Shelly and reports verification only while the persisted evidence remains fresh. No control or measurement permission is granted by verification. A separate regression confirms EM50 reconciliation preserves existing authority and does not add switching or power approval.

**Runtime and approval status:** source tests cover the local authorized EM50 evidence path and stale UI projection. This milestone has not yet run the refreshed action against the physical EM50 through an authenticated live Portal, and no power-approval request has been submitted. The separate administrator approval for EM50 `em1:0` / `power` remains required before any electrical observation can be admitted. The last reported physical status value is historical and is not presented here as a current sample.

**Site-authority foundation:** safe `.env.example` values and an administrator-only diagnostic report `ENERGRID_INSTANCE_ID` and `ENERGRID_INSTANCE_MODE` (`development-isolated`, `site-authority`, or `observer`). The diagnostic does not enforce ID uniqueness, authenticate an observer, transfer authority, or prove deployment. The current internal observation ingress must not be exposed to arbitrary observer payloads, and the existing operator-attested site-local evidence intake is not machine authentication. Secure observer-to-site-Core delivery remains a separate required boundary: authenticated observer identity, exact tenant/site/scope/device/component assignment, freshness, replay/ordering protection, and admission through the canonical writer. Do not work around this by widening scopes or trusting an operator report as machine evidence.

**Next actions:** rebuild/restart only the local development API, use the existing authenticated Home Portal to refresh exact EM50 identity/component evidence, inspect the result without approving power, and keep Home production on Pi 5 untouched. Separately plan the smallest authenticated observer-to-authority boundary before moving Mac-observed Eero data into Pi-owned state. The historical M1–M3 entries below remain their own dated checkpoints and are not deployment claims.

### M1.4e — scoped commissioning-event persistence (locally validated, not deployed)

New commissioning events use `event-v2:<encoded tenant>:<encoded site>:<encoded device>:<encoded event id>` and require explicit ownership. Scoped readers return only exact tenant/site/device matches. The Portal commissioning-event endpoint resolves its authorized site from the authenticated principal and checks the device in that scope before reading history. The registry rejects ambiguous device-ID-only event writes; callers with trusted ownership can supply it explicitly. Legacy `event:<device id>:<event id>` records are preserved but **not** exposed through scoped reads or automatically assigned to any site; offline inventory and a reviewed migration are still required. This is not a durable, tamper-evident audit ledger.

**Scope limitation:** other legacy Portal commissioning mutation routes still resolve devices by ID alone; this change does not make them tenant-isolated. Run the focused storage, Portal, and registry tests, API typecheck, and broad regression suite before acceptance. No live LevelDB migration or deployment is included.

### M1.4d candidate — scoped installation/proposal persistence (test verification pending)

`DeviceInstallationStore` writes new installations under `installation-v2:<encoded tenant>:<encoded site>:<encoded device>` and new proposals under `installation-proposal-v2:<encoded tenant>:<encoded site>:<encoded proposal id>`. All installation/proposal reads require explicit tenant/site scope; the store does not accept site-only lookup. Legacy reads use their embedded tenant/site ownership and never infer missing ownership. All-site bootstrap retains a versioned record in preference to its legacy copy. New proposal decisions must hide older pending legacy copies.

This candidate **does not migrate, rewrite or delete legacy keys**, and does not address unscoped commissioning event keys or the Portal's event endpoint. Before rollout: inspect an offline LevelDB copy for missing ownership and duplicate/conflicting legacy records, back up the live store, validate restart and older-version rollback constraints, then run the full tests. Reverting application code after v2 writes would not expose those writes to an older binary; a backup alone is not a lossless rollback after subsequent writes. No live DB, deployment, or hardware validation has occurred.

## M1.4 — Tenant/site/device identity corrections (in progress, not yet accepted)

**M1.4a committed (`bb970a7`):** the registry's all-site inventory previously deduplicated by `device.id` alone. It now uses the existing encoded tenant/site/device key to retain distinct devices across sites and tenants while still preferring the higher-priority record *within the same scope*. A regression test constructs identical logical IDs across three scopes. The operator reported focused Jest, TypeScript and docs checks green before commit.

**M1.4b candidate (runtime observation projection; verification pending):** scope operational state, approved field ownership, approved observations and replay-ID suppression by the existing encoded tenant/site/device key. Trusted MQTT/HTTP observation routes now forward their independently resolved scope. This isolates measurement values and status projection; it does **not** scope command tracking, guarantee identity for legacy unscoped ingestion, or change LevelDB keys. Run focused registry/observation tests and all relevant API integration checks before acceptance.

**Still open:** The registry command tracker and its reconciliation still use `deviceId` without owner scope. Legacy MQTT status and other unscoped callers can fall back to the configured Home scope rather than an independently resolved owner; this is compatibility behavior, **not a cross-tenant authorization guarantee**. The legacy telemetry ingress also accepts identity fields from payload-shaped data and needs a separate verified authority-path review. `DeviceInstallationStore` LevelDB installations use `installation:${siteId}:${deviceId}`; proposal keys omit tenant; event keys use only device ID. Do **not** change these persisted key formats without a read-only collision inventory, backward-compatible migration/restart tests and a verified rollback plan. M1.4a does **not** establish complete cross-tenant isolation or authorize new device control.

## Weather forecast tile renderer V1 status

The renderer and public Core tile route are in the weather release commit, with focused coverage for run-pinned WCS requests, PixelIsArea alignment, transparent zero, missing data, intensity values, adjacent XYZ continuity, exhausted WCS no-data, network failure and recovery. The service validates each requested run and valid hour against DWD capabilities. Per-process upstream work is capped at four active requests and 24 queued; peer queues are round-robin, capped at three active and 16 queued per socket address. Core enables permissive CORS globally, and a reverse proxy collapses caller identity unless it is explicitly and safely propagated. These limits do not replace ingress-level per-client request limits.

**Weather upstream reliability (Patch 04, focused local verification passed; not deployed):** DWD upstream fetches already have a 12-second HTTP deadline, per-process concurrency caps, and no-data retries. Patch 04 additionally expires queued DWD work after 8 seconds, removes timed-out entries without consuming slots, and preserves peer rotation. Both river HTML sources share a 10-second fetch deadline and 1 MiB response cap; provider failures continue to return unavailable readings rather than invented measurements. Focused transport tests are included. This does **not** implement caller-disconnect cancellation, multi-process admission control, upstream health telemetry, authoritative river timestamps, or public ingress rate limits. Focused tests and build checks passed locally. Production routing, runtime acceptance and deployment remain unverified.

**Release status: BLOCKED on production routing and deployment ownership.** Local acceptance on 3 November 2026 passed: Core capabilities returned run `2026-11-03T06:00:00.000Z`; the browser rendered observed-to-forecast frames, subsequent hours, pan and zoom; outage/recovery was visible; and a direct tile returned a valid 256×256 PNG. Production checks found `https://energrid.bg/core/weather/performance` returns 200, but `/core/weather/radar-forecast/capabilities` returns 404. ## River observation provenance — M1a source patch (5 November 2026; pending local verification)

APPD's daily page date is **not** a per-station measurement instant; some readings may be the preceding day's. DanubePortal publishes local-looking per-gauge date/time strings without an explicit UTC offset. The adapters now preserve the reported date/time separately, record actual HTTP fetch time as `fetchedAt`, and set `observedAt=null`/an explicit unverified basis instead of manufacturing an exact UTC measurement time. The existing hourly `river_readings` writer refuses newly fetched observations without a verified observation instant.
