# Shelly Pro 2PM switch-mode reconciliation and MQTT measurements

This page documents the scoped implementation for reconciling accepted site-local RPC evidence to already-enrolled Shelly components, then independently proposing MQTT measurements. Reconciliation preserves device IDs, names, rooms, physical inventory association, history, observation authority and control configuration. The Mac LAB activation status is reported separately by the operator.

## Current profile evidence

The operator reports that the physical Shelly at `192.168.1.166` now uses Switch mode and exposes `switch:0` and `switch:1`. The earlier `cover:0` response describes a historical profile and must not be used as current capability evidence. A fresh RPC identity and per-component status report is required before producing a current candidate. The implementation never infers relay channels from `SPSW-202PE16EU` or `Pro2PM` alone.

The existing collector reads `Shelly.GetComponents`, follows bounded pages, and verifies each supported switch/meter component using its own read-only status RPC. It derives measurement capability only from numeric fields in the matching response. Shelly cumulative energy values reported in Wh are normalized to kWh; import and returned/export totals remain distinct cumulative counters. Other reported components such as `input:0` and `input:1` are not turned into onboarding candidates by this focused workflow.

## Site-local report intake

The narrow Portal API accepts a report only from an authenticated Portal administrator and a server-configured observer allowlist bound to the active tenant/site, configured network scope, observer interface/address and directly connected route. The report is a single-target read-only RPC result: it must contain exactly one in-scope endpoint and explicitly marks host discovery incomplete; no subnet scan is required or accepted. It also requires an exact expected Shelly identity, consistent MAC evidence when an observed MAC is provided, individually verified `switch:N` or `em1:N` status responses, and fresh timestamps. Ownership is assigned by the server; fields in the report cannot select a tenant or site. The accepted report enters site-owned Discovery Memory. Exact matches against persisted, enrolled components in the authorized tenant/site are shown as reconciliation proposals instead of being registered as duplicate candidates. Other-site matches and same-site identity mismatches are suppressed and surfaced as conflicts. An administrator may separately record verified identity/component metadata on an exact existing enrollment; that action leaves enrollment placement, physical inventory identity, history, measurement authority and control authority unchanged. Repeating the same immutable evidence is idempotent. New, unmatched components still use the existing pending-candidate lifecycle.

The report source is **operator-attested, not cryptographically signed by the Pi**. The Portal administrator session, allowlist, strict scope/identity validation and explicit candidate review constrain intake, but do not prove that the JSON was emitted by the observer. The snapshot records this limitation. Before automated or lower-trust intake, add observer-origin signatures verified against server-configured public keys and update the isolated Linux runner to sign its output.

## Historical profile conflicts and operator review

Fresh switch evidence is compared with existing same-site records for the same Shelly physical ID. Historical `cover:N`, `switch:N` or `em1:N` components absent from the fresh profile are preserved and marked as conflicts; nothing is deleted or silently relabeled. Existing exact component enrollments remain in place; reconciliation does not create another logical record or change its room.

Enrollment or identity reconciliation does not grant measurement or control authority. Accepted historical RPC evidence may be attached to an exact existing enrollment for traceability and to populate a review, but the Portal labels its provenance and timestamps and marks it historical. Recording new measurement authority requires identity and component evidence no older than 15 minutes; the API checks this again at approval time. Power and cumulative energy fields are proposed only when present in component status. Each field requires separate operator approval and site-owned installation authority. The approval binds the configured broker endpoint, exact event topic, logical component, and selected fields. A custom topic such as `shelly/washer@other/events/rpc` is supported. Neither broker/topic routing nor payload identity proves physical identity. The runtime subscriber must still use the approved broker, and each source message must map to the independently RPC-verified, enrolled component and pass the persisted per-field approval. Accepted MQTT observations use the shared deterministic observation ingress and history writer. No relay action is enabled by measurement approval.

For Shelly `NotifyStatus`, the MQTT adapter keeps the full status and non-measurement fields available to Bus/evidence processing, while the approved observation route projects only canonical `power` (W), `energy_import_total` (kWh), and `energy_export_total` (kWh) values into measurement ingress. Shelly cumulative energy reported in Wh is normalized to kWh once at the adapter. Unsupported fields such as output state, current, voltage, and duplicate raw energy aliases are not submitted as approved measurements. A present but malformed supported field is retained as an invalid reading and rejected explicitly; an absent field is not synthesized as zero. The canonical projection still passes through the exact device, topic, site-owned installation, enrollment, and per-field approval checks.

The Portal evidence review accepts a JSON report through `POST /portal/network/site-local-shelly-evidence` and presents exact existing component matches. An already accepted, site-owned report can be reopened without reimport through `GET /portal/network/site-local-shelly-evidence/:scanId/review`; this is read-only and reproduces the current matches and conflicts. The administrator's separate “Record verified identity” action uses `POST /portal/network/site-local-shelly-evidence/:scanId/reconcile`. After reconciliation, device details show the source, observer, endpoint, timestamps, freshness status and one separate proposal per RPC-confirmed measurement. Approval is a later, separate action at `POST /portal/devices/:deviceId/shelly-observation-approval`, requiring fresh evidence, the broker, event topic and selected field. Do not infer a current MQTT topic from the reported Shelly ID; use observed Bus evidence.

## Activation boundary

The isolated implementation is activated only through the controlled local LAB release process. Fresh single-device Pi evidence is required before measurement authority is recorded; accepted older evidence remains historical and cannot bypass that freshness requirement. Importing evidence creates a review proposal, not an enrollment, measurement approval or control binding. The application code does not reconfigure the MQTT broker or physical device.
