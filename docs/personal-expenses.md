# Personal expenses

## Scope

Personal Expenses is an account-scoped feature in the Energrid Portal. It stores personal transactions separately from device, site, energy-telemetry and household-inventory records. Every API request requires an Energrid access token; the server scopes reads, writes, imports and deletion to the authenticated account ID.

The `/personal-finance` account-scoped API and Assistant use PostgreSQL as the sole active transaction store. The obsolete `/personal-expenses` LevelDB HTTP API and its runtime storage/capture services have been retired. Its text proposal parser is local and provider-independent; proposals remain drafts until an authenticated user confirms them. Receipt Intelligence can extract a JPEG or PNG after the signed-in user explicitly opts in to cloud processing. Extraction creates a review-required draft; it does not create an expense until the user reviews and confirms it. Payment integrations remain out of scope. Account-scoped assistant expense tools are registered through the HouseAgent integration.

## Record and currency behavior

V2 keeps original amount and currency separately from EUR amount and FX provenance. Decimal operations use base-10 integer arithmetic and PostgreSQL `numeric(38,18)`; values outside that exact storage range are rejected before persistence. Computed EUR values are rounded to cents using ties-to-even. Imported EUR amounts and FX provenance are preserved as supplied. Historical BGN records without a stored EUR amount or FX rate remain unconverted and are excluded from EUR totals; the importer does not invent an exchange rate. New expenses are restricted to EUR and USD. Currency values use three-letter ISO 4217 codes, with currency-aware minor-unit precision for item totals.

New configurable categories have account-scoped stable IDs, optional descriptions and parents, and active/archived state. Create, rename, and archive operations run transactionally and append immutable category audit events. Active names are unique case-insensitively within an account; hierarchies cannot contain cycles, and a parent with active children cannot be archived. Expenses linked to a managed category retain its stable ID, so renaming updates the displayed label without changing its classification; summaries group linked expenses by ID and legacy text expenses by their original label. Historical imports remain unlinked free-text categories and are never automatically reclassified. Legacy MongoDB Extended JSON dates (`{"$date": ...}`), object IDs (`{"$oid": ...}`), JSON arrays, and wrapper objects containing an `expenses`, `records` or `data` array are accepted. JSON Lines files are also supported by the Portal importer.

## Import behavior

The PostgreSQL importer provides a transactional repository import operation with account-scoped source and legacy-record unique keys; its batch either commits fully or rolls back fully. Expense listing and summaries read PostgreSQL only; no runtime LevelDB bridge or backfill is performed.

`application/historical-reconciliation.ts` provides a database-independent reconciliation function for exported snapshots. It reports source counts, exact original-currency and month/currency totals, account mismatches, and malformed rows. An identical namespaced `legacy-mongo` source ID is the only confirmed duplicate; similar transactions are review candidates and are never automatically discarded. Date, amount and currency alone do not constitute a candidate. This function does not open MongoDB, PostgreSQL or LevelDB and does not write records. A migration is not ready to commit while there are possible duplicates, validation errors, or account mismatches.

The local PostgreSQL reconciliation on November 5, 2026 confirmed 441 active `legacy-mongo` records for one account: 266 BGN (34,611.94 BGN) and 175 EUR (8,893.97 EUR), all with unique source IDs/legacy IDs, valid identity mapping and non-null EUR values. This is aggregate/identity evidence, not a byte-for-byte comparison against the Mongo export or proof of production deployment. Retain the Mongo export and a PostgreSQL backup before deploying the removal. Keep any historical `source_kind`, `source_id`, `legacy_record_id`, and stored FX metadata: they are audit provenance, not active LevelDB dependencies.

The PostgreSQL import still accepts batches of up to 10,000 records, checks stored source IDs for duplicates and retries idempotently. It no longer requires LevelDB availability. Import file handling remains a separate archival workflow, not a live-store dependency.

## Storage and privacy

PostgreSQL contains tables for merchants, expense drafts, expenses, line items, receipt metadata and immutable provenance. Receipt image files are stored separately under `~/.energrid/private-receipts` by default, configurable with `PERSONAL_FINANCE_RECEIPTS_DIR`; account directories use mode `0700`, files use mode `0600`, and API responses omit private storage keys. The receipt migration is additive and its down migration intentionally preserves financial records.

Receipt extraction sends an image to the configured OpenAI document-understanding adapter only when the request includes explicit consent and `ENERGRID_LLM_MODE=cloud-enabled`, the configured provider is OpenAI, and an API key is available. The adapter limits request time and retries, requests a strict typed schema, and treats text found in the image as untrusted data. For receipt item suggestions, the account's active category names are supplied as the allowed choices; the application canonicalizes returned names against that account's categories and drops unknown or archived suggestions. Item suggestions are based on product-line content, not merchant identity. A draft-level category suggestion is selected deterministically from the largest sum of suggested item line totals. These values remain suggestions: the user must review the draft, itemization or total-only choice, and then confirm it before an expense is written. Duplicate image content is detected by an account-scoped SHA-256 hash. Possible existing expense matches are suggestions only. Invalid draft proposals are cleaned up before any database write; a failed match lookup after draft creation must never delete its committed private image; on an uncertain draft-write outcome, an absent receipt lookup is not sufficient to delete the image, because the commit might still complete. Receipt content can be viewed only through the authenticated, account-scoped API; image deletion marks the document deleted and removes its local file while preserving receipt metadata. Banking credentials and external financial APIs remain out of scope. The Finance text proposal endpoint uses a local parser; no legacy capture endpoint remains.

Receipt extraction V1.1 retains each printed row as a typed document entry (purchase, discount, adjustment, subtotal, final total or payment); only purchase rows become expense items. Exact reconciliation uses purchase-line amounts plus signed adjustments, and an adjustment that may already be embedded in a line remains unresolved until reviewed. The original extraction and printed total remain immutable provenance; a separate nullable reviewed total/currency records the user's explicit correction, introduced by `1793361600000_personal-finance-reviewed-receipt-total-v1-1.js`. The review endpoint returns a server-calculated reconciliation, and confirmation still repeats the exact checks transactionally. This migration is additive and has not been applied to any database as part of this change.

## API surface

- `POST /personal-finance/drafts/propose` creates a locally extracted, unconfirmed draft; `GET /personal-finance/drafts/:id` reads it; `POST .../:id/confirm` confirms it transactionally; `POST .../:id/reject` rejects it.
- `POST /personal-finance/receipts/extract` accepts one JPEG/PNG file up to 10 MiB plus `cloudDataConsent=true`; it returns a review-required draft and account-scoped possible matches, without confirming an expense.
- `PATCH /personal-finance/drafts/:id` saves explicit receipt review choices, including reviewed itemization or total-only treatment and adjustments. The existing draft confirmation endpoint remains the separate action that records the expense.
- `GET /personal-finance/receipts/:id/content` streams the account-owned image with private/no-store headers; `DELETE .../content` deletes the file but keeps its metadata; `POST .../attach` associates receipt metadata with an existing expense in the same account.
- `GET /personal-finance/expenses` queries PostgreSQL (including migrated historical records) with account-scoped filters/limits; `GET /personal-finance/summary` returns PostgreSQL EUR totals, unconverted counts, and calendar-month daily pace. Both Portal and Assistant use the same application-level summary policy.
- `GET /personal-finance/categories` lists active categories; `POST /personal-finance/categories` creates one; `PATCH /personal-finance/categories/:id` renames or reparents one; `POST /personal-finance/categories/:id/archive` archives it without deleting history.
- `POST /personal-finance/expenses/import` accepts legacy records with stable `_id`, `legacyRecordId`, or `id` keys and stores each submitted batch transactionally.

All V2 ownership derives from the authenticated account principal. The API does not use site selection or request-body account IDs. The Assistant exposes verified-account-only Finance operations (proposal, draft confirmation and rejection, expense queries, and spending summaries). PostgreSQL is configured through the existing `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, and optional `PGSSL` convention; local development may use the existing loopback-only `AUTH_DATABASE_URL` override. Applying the migration remains an explicit operational step.

Product summaries aggregate line-item totals in the product's original currency and unit; they do not convert mixed-currency product prices into EUR.

The implementation lives in `apps/api/src/app/modules/expenses/` and `apps/portal/src/components/expenses/ExpensesDashboard.vue`.

## Product boundary

Finance domain types, decimal rules, validation and application use cases are kept under the expenses domain/application boundaries and do not depend on Energrid sites, devices, households, Letta or Portal code. The PostgreSQL adapter, Nest controllers and account-principal adapter remain monorepo consumers/integration points. A later standalone extraction can move the domain and application packages unchanged first, then provide a standalone authentication adapter and API host; Portal and Assistant should remain clients of those operations. No service split or deployment change is part of this milestone.

The application service is constructed behind explicit repository and extraction ports, and its category operations accept a framework-independent finance account/actor context. The Energrid controller is responsible for deriving that context from the verified authenticated principal. The PostgreSQL schema still references Energrid's `auth.users` table; that is an adapter-level extraction dependency. Imported historical provenance remains stored in PostgreSQL without consulting LevelDB. Currency reports currently use EUR, the account reporting-currency preference is not yet configurable, and no rates are guessed for unconverted transactions.

## PostgreSQL-only Finance reads (M4)

Portal `GET /personal-finance/summary` and Assistant `finance.summarize_spending` call `PersonalFinanceApplication.summarizeSpending` directly. It delegates to the PostgreSQL repository and adds the existing calendar-month daily pace. Expense listing has one PostgreSQL query path; the former LevelDB merge, warning contract, dual-store duplicate lookup and legacy HTTP controller have been removed. No extra application boundary was introduced.

The old on-disk LevelDB directory is **not** deleted by this code patch. Keep any archival backup intact. Record and FX provenance remain immutable historical evidence.

## Receipt image deletion retries (M5.2)

`DELETE /personal-finance/receipts/:id/content` marks the account-scoped receipt document deleted in PostgreSQL before removing its private file. Repeated deletion succeeds if the image, account directory, or storage root is already absent. Invalid ownership, symlinks, and filesystem errors other than `ENOENT` still fail. If file deletion fails after the database marker is saved, the error is returned and another deletion request retries file removal. The database and filesystem do not form one atomic transaction.
